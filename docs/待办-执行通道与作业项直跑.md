## T1 · 放开 role=field 的执行限制（待细化）

**现状（已实测确认）**

服务端 `server.py` 的 `/ws/browser/{room}` 对话通道硬性限制：

```python
if ws_role in ("field", "guest"):
    if not user_message.startswith("[QUICK_ACTION:"):
        await websocket.send_json({"type": "error",
            "content": "上门工程师账号无对话权限——可使用「连接你的电脑」与快捷工具，对话诊断由远程工程师处理。"})
        continue
```

**影响**

- 现场作业台 `/field` 主要使用者就是上门工程师（role=field）
- 53 个作业项里只有 **14 个**配了独立 HTTP 端点（直跑可用）
- 其余 **39 个**走「AI 执行通道」（WS 对话）→ 被上面这条拦掉 → 页面报「执行通道错误」
- 因此：**批量执行对 field 账号只有 14 项可用**；对 expert/admin 不受影响

**要细化的问题**

1. 白名单边界：哪些命令允许 field 直接跑（只读诊断类？还是也算上写操作但走门禁）
2. 权限模型：field 是否允许「不经对话、但经服务端脚本化执行」——建议 **允许执行、不允许自由对话**
3. 是否给 field 保留「提一句自然语言让 AI 判读」的能力（当前用 `/api/ai_qa` 已可，不占对话权）
4. 审计：field 直跑的命令如何留痕（现有 `messages` + `audit` 是否够）

**建议做法（待主人确认）**

- 服务端新增 `POST /api/tools/run_item {room_code, key}`：按作业项 key 映射到白名单命令 → `execute_bridge_command` → 返回真实输出
- 该接口对 **所有角色** 开放（只读项）；写操作/刷写仍需原有门禁（工号/快照/双人）
- 前端 `runAction` 优先调这个接口；只有「需要 AI 现场生成命令」的极少数场景才回落到 WS 对话

## T2（原 P5）· 作业项直跑端点

**目标**：53 个作业项都有服务端直执行路径，不经 AI、不需对话权限。

**收益**

| 收益 | 说明 |
|---|---|
| 上门工程师可用 | 22 位 field 账号能真正用批量执行 |
| 更快 | 省去大模型生成命令的时间（当前走 AI 通道每项要多等 10~60 秒） |
| 更稳 | 命令固定可回归，不受模型波动影响；同一项每次跑的东西一致 |
| 更安全 | 命令白名单写死在服务端，模型无法自由发挥 |
| 可离线审计 | 每条命令与输出都落在 `messages`，与 AI 无关 |

**实现路径（分批，先高频）**

1. 第一批（蓝屏/硬盘/温度/日志类，最常用）：`bsod` `disk` `thermal` `slow` `system` `hw_winlogs` `hw_dump` `hw_sio`
2. 第二批（外设/网络/电池/启动）：`network` `usb` `audio` `display` `battery` `startup` `printer` `camera`
3. 第三批（写操作类，需避开门禁设计再谈）：`sfc` `adware` `activation` `service` `bootfail` `logspace`
4. 前端 `paintGrid` 里给已配端点的项打「直跑」标记；未配的显示「需 AI 通道」并禁用批量勾选

**验收标准**

- field 账号勾选任意 5 个只读项 → 批量执行全部成功，无「执行通道错误」
- 执行耗时相比 AI 通道下降 ≥ 50%
- 每项输出结构与 AI 通道一致（可进证据链）

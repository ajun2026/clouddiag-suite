# C3 · `_find_sos_root()` 上溯越界，读到宿主机数据

**发生时间**：2026-09-29（外部反馈）
**类别**：安全（数据越界 / 隔离失效）
**严重度**：🔴 高（报告内容可能记录的是服务器而非客户机）
**影响版本**：≤ v1.0.8

---

## 现象

Linux 日志包分析时，若压缩包内**只有 `log/` 目录、没有 `var/log/`**：

- 分析结果里的「操作系统名称」显示的是 **Log Analyzer 所在服务器自己的系统**（如 `Ubuntu`），
  而不是客户机的系统；
- 报告的可信度被污染（分析对象被悄悄替换成了宿主机）；
- 在部分环境还会因全盘遍历撞到读不了的条目（`/proc/<pid>/map_files`）而使整次分析失败。

## 根因

`analyzers/linux.py` 的 `_find_sos_root(log_dir)` 原实现：

```python
for p in [log_dir] + list(log_dir.parents):      # 无界上溯，一直到 /
    if (p / "etc").is_dir() or (p / "proc").is_dir():   # `/` 必然命中（or + /etc 存在）
        return p
```

触发链：

1. `find_log_dir()` 的 Linux 分支 2b —— 包内只有 `log/syslog`、没有 `var/log` 时，
   返回 `found.parent`，即 `<解压目录>/log`（父目录名不是 `var`）；
2. `_find_sos_root()` 因此走不进「`log` + 父目录 `var` → 上两级」这条可靠分支，
   转而进入无界上溯循环；
3. 上溯到 `/` 时 `(Path('/')/'etc').is_dir()` 为真 → **root 被判定为 `/`**；
4. 随后 `root.rglob('*os-release*')` 等调用在**整个文件系统**上搜索，命中的是宿主机的
   `/etc/os-release` → 把它当成客户机系统报出去。

本机实测（探针包只有 `log/syslog`）：

| 版本 | `_find_sos_root` 返回 | 分析出的 OS 名称 |
|---|---|---|
| 修复前 | `/` | 宿主机/其他包的 `os-release` 内容（跨包污染） |
| 修复后 | `<解压目录>/log` | （无，正确地留空） |

## 影响范围

- 所有「Linux 日志包内没有 `var/log/`」的上传（常见于只抓 `log/` 的自定义采集脚本）。
- 影响面是**报告可信度**：系统概览里的 OS / 部分硬件信息可能来自服务器而非客户机。

## 处置过程

```python
# 修复三原则（v1.0.9）
1) 只在包内浅层上溯（最多 3 层）
2) 绝不越过文件系统根（cur.parent == cur 立即停）
3) 标记判定由 `or` 改为 `and`（真 sosreport 根同时含 etc/ 与 proc/）
# 找不到结构 → 停在 log_dir 本身，并打 WARNING 留痕
```

同时给 `read_first()` 的 `stat()` / `open()` 加 `try/except OSError`——
越界或包内存在读不了的条目时，不再让**整次分析**因单个文件失败。

回归验证：sosreport 形态包（含 `etc/os-release` + `proc/version` + `var/log`）
解析结果与修复前一致（OS 名 = 包内值、内核 = 包内值），未发生功能退化。

## 预防措施

- **任何"向上找根目录"的推理，都必须有明确边界**：只在输入子树内活动，越界即失败（而非成功）。
- 判定条件涉及系统目录（`etc`/`proc`）时，禁止用 `or` 组合——宿主机的 `/` 永远满足。
- 文件读取类操作一律加异常保护，避免单点失败摧毁整条分析链。

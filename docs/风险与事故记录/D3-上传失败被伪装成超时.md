# D3 · 上传失败被伪装成"600s 超时"

**发生时间**：2026-09-29（外部反馈）
**类别**：运维 / 可诊断性
**严重度**：🔴 高（任何上传失败的真实原因都看不到）
**影响版本**：≤ v1.0.8

---

## 现象

从工作台触发「采集日志 → 上传到 IDG」（`POST /api/tools/upload`）时，若上传其实**已经失败**
（例如 IDG 侧缺 `7z` 导致 `.7z` 解压报错、或解压失败返回 400），前端**只看到**：

```
上传超时（600s）——文件可能过大或网络慢
```

真实原因（`IDG 上传失败: 解压失败：FileNotFoundError...`）被完全掩盖，
使用方会去排查网络与文件大小，方向被带偏。

## 根因

失败结果**没有回写等待中的 future**，只依赖桥接器的 WebSocket 回传：

```
/api/tools/upload   → 建 future，放进 room.pending_commands[fid]，等结果（600s）
/api/bridge/upload  → 只有【成功】分支才 set_result("[upjob] job=…")   ← 问题在这
                      失败分支直接 return 502，future 始终未完成
桥接器 WS            → file_upload_error / file_upload_result 是唯一的失败回传通道
```

于是：**桥接器 WS 一旦断开（客户机网络异常时最常见），失败结果就永远到不了服务端**，
`/api/tools/upload` 只能干等到 600s 上限，再报一个把责任推给"网络/大文件"的超时。

代码上还叠加了两个缺陷：

- `/api/tools/upload` 对**同一个 future 连续 `await wait_for` 两次**（600s + 600s），
  且第一次的 `finally` 就把 `fid` 从 `pending_commands` 摘掉——桥接器后续回包找不到 `fid`；
- 结束分支只区分「成功 `[upjob]`」与「其它 → 上传失败」，`[upload_fail]` / `[file_error]`
  的真实原因被压缩进 200 字符的兜底文案里。

## 处置过程

```python
# v1.0.9
1) 新增 _resolve_pending(room_code, fid, value) —— 成功与失败共用同一回写入口
2) /api/bridge/upload 失败分支：立刻 _resolve_pending("[upload_fail] IDG 上传失败: …")
3) /api/tools/upload：单次等待、单处 pop；[upload_fail]/[file_error] 原样透出（502）
4) 超时文案补上可操作信息（"检查客户机→服务器网络，或文件是否过大"）
```

端到端验证（本机真链路：模拟桥接器 WS + 真 IDG 拒绝）：

| 版本 | 工具调用耗时 | 返回内容 |
|---|---|---|
| 修复前 | ~600s（干等上限） | 「上传超时」 |
| 修复后 | **0.1s** | `上传失败: IDG 上传失败: 解压失败：…`（HTTP 502） |

## 预防措施

- **异步等待（future/promise）必须在所有出口都收敛**：成功、失败、异常、超时——
  只 resolve 成功路径，等价于把失败伪装成超时。
- 跨进程/跨连接的操作，**不要让唯一的结果通道是长连接**（WS 断了就什么都不知道）；
  同步返回的 HTTP 路径也要主动回写结果。
- 同一个 future 只在一处 `pop`、只等一次；重复 `wait_for` 会掩盖真实时序。
- 对外文案禁止把"未知失败"归因为某一种具体原因（如"网络慢"）。

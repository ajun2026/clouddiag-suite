对 v1.0.7（commit `2f01c54af4`）执行了 API 层 84 项探测 + WebSocket 层 3 项探测 +

## 🔴 P1-1 · `/ws/browser/{code}` 鉴权绕过

**问题**
`ws_browser` 只校验「房间存在」，对登录会话只是「读出来当角色用」，**没有在会话缺失时拒绝**：

```python
# 修复前
_ws_token = websocket.cookies.get("user_token", "")
_ws_sess = USER_SESSIONS.get(_ws_token)
ws_role = (_ws_sess or {}).get("role", "")   # 无会话时 ws_role="" 仍继续
```

**影响**
未认证者只要拿到 8 位房间码（房间码会随 `.bat`/`.ps1` 一键连接脚本、聊天记录外发）即可：
1. 覆盖 `room.browser_ws`，顶掉合法工程师的连接；
2. 发送 `type=chat` 驱动 AI 在客户机上下发命令（桥接器侧含 Tier 3 修改类工具）。

**修复**（v1.0.8）
与 `_require_user` 口径一致：校验会话**存在且未过期**，通过后滑动续期。

**实测对比**

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 有效会话 | 连接成功 | ✅ 连接成功 |
| 无效会话 | ❌ **也能连** | ✅ 拒绝：「未登录或会话已过期」 |
| 无 cookie | ❌ **也能连** | ✅ 拒绝（同上） |

## 🔴 P1-2 · 存储型 XSS（SN／机型／房间码未转义）

**问题**
`dashboard.html` 已定义 `escapeHtml()`，但 9 处 `innerHTML` 拼接直接塞入接口返回的 `r.sn` /
`r.machine_model` / `r.room_code`，未调用转义。这些字段由工程师自由输入，服务端当时无校验。

**开发端扩大排查**：实际受影响 **20 处**（报告指出 9 处，另有 11 处在表格行与简版 option 拼接中）：

| 类型 | 数量 | 修复方式 |
|---|---|---|
| `<option>` 多行拼接 | 9 | 改 `createElement` + `textContent`（彻底避免 HTML 解析） |
| 表格行 `<td>` / 按钮 onclick 拼接 | 6 | 加 `escapeHtml()` |
| 简版 `<option>` 拼接 | 4 | 加 `escapeHtml()` |
| 其他 | 1 | 加 `escapeHtml()` |

**影响**：任何查看工作台「工具」页签的用户（含 admin）都会被触发，可窃取会话、
以受害者身份操作、配合管理员权限提权；载荷持久化在数据库中。

**修复**：前端全量转义 + **服务端同步加字符白名单与长度上限**（见 P3-3），从源头拦截载荷。

**验证**：dashboard.html 未转义的 `innerHTML` + `r.sn` 拼接点 **20 → 0**。

## 🟠 P2-1 · 非法 JSON 请求体 → 500

**问题**：4 个接口（admin/login、auth/login、change_password、create_room）直接用裸
`await request.json()`，请求体非法时抛 `JSONDecodeError` → 500，且每次写入数十行 traceback。

**开发端扩大排查**：实际有 **9 处** 裸调用（另有 ai_providers_create/update、
admin_create_user、admin_reset_password、admin_delete_room）。

**修复**：统一封装 `_safe_json(request)`，解析失败或非 dict 一律返回 `{}`，
由各接口自己的字段校验返回 400。

**验证**：非法 JSON / 空 body / 数组 body → 全部 401/400，**不再 500**。

## 🟠 P2-2 · `/api/rooms` 字段类型错误 → 500

**问题**：`(body.get("sn") or "").strip()` —— 传入数组/对象时 `AttributeError` → 500。

**修复**：加类型安全提取（非 str 一律当空处理），与 P3-3 的白名单校验合并实现。

**验证**：`{"sn": ["a","b"]}` → 400。

## 🟡 P3-1 · 版本号硬编码

**问题**：管理后台 HTML 与启动日志硬编码 `v1.0.0`，与 `/api/health` 的版本不一致。

**修复**：抽模块级常量 `APP_VERSION`，三处统一引用（管理后台 HTML 用 `replace` 占位符注入，
避免 HTML/CSS 的 114 处花括号在 f-string 中需转义）。

---

## 🟡 P3-2 · 重复元素 ID

**问题**：`diag.html` 中 `live-steps` / `live-wait` 各出现 3 次（不同渲染模板）。

**修复**：改为 `class` + `querySelector`，消除 ID 冲突隐患。

---

## 🟡 P3-3 · SN／工单号无长度上限与字符校验

**问题**：10000 字符的 SN 可成功入库；并且为存储型 XSS 提供载荷。

**修复**：服务端加字符白名单（拒绝 `<>&"';|`$(){}[]`）+ 长度上限
（SN/工单 ≤ 64、机型 ≤ 128），超限返回 400 中文提示。

**验证**：10000 字符 SN → 400；`<img src=x onerror=alert(1)>` → 400。

---

## 🟡 P3-4 · IDG 缺少健康检查端点

**问题**：`log-analyzer` 无 `/api/health`，与 server 接口命名不一致，不利于统一监控与部署自检。

**修复**：新增 `/api/health`，返回 `{"status":"ok","service":"log-analyzer","version":...}`。

## 教训

1. **「读出来用」不等于「校验」**：会话读出来当角色用，但缺失时未拒绝，等于没有鉴权。
   凡是"身份相关"的分支，必须显式写 `if not 有效: 拒绝`。
2. **审计要扩大到同类模式**：报告指出 9 处 XSS / 4 处 JSON，实际各为 20 处 / 9 处。
   收到问题后应**全库搜索同一模式**，而不是只改报告列出的行号。
3. **前端与服务端双重防护**：转义（前端）+ 白名单（服务端）——只做一侧都可能被绕过或遗漏。
4. **异常入参是常态**：外部扫描器、被截断的请求、代理改写 body 都会产生非法 JSON，
   必须统一走安全解析函数。
5. **版本号单一来源**：多处硬编码必然漂移，抽常量是零成本做法。

## T3 摘要（2026-10-29 记录 · 后续再设计）

**现状**：登录页「忘记密码」= `alert('请联系管理员重置密码')`，没有任何自助能力；
真正的重置只有一条路——管理员登录后台 → 用户管理 → 重置密码 → 手工告知本人。
问题：管理员不在线就没人能改、员工不知道找谁、新密码还要在聊天里传。

**候选方案**

| 方案 | 做法 | 成本 | 依赖 |
|---|---|---|---|
| A 人工重置 | 维持现状，仅把文案写清「联系谁」 | 10 分钟 | 无 |
| **B 一次性重置码** | 管理员后台点「生成重置码」（6 位 / 20 分钟 / 一次性）→ 电话报给本人；登录页输入 工号 + 重置码 + 新密码自助改 | 半天 | 无（**建议先做这个**） |
| C 邮件自助重置 | 输入工号 → 发重置链接到邮箱（30 分钟一次性 token）→ 点链接设新密码 | 1.5 天 | **SMTP / 内部邮件中继（关键卡点，需 IT 提供）** |
| D 企业 SSO/LDAP | 用域账号登录，系统不存密码 | 3~5 天 | IT 配合 |

**C 方案技术要点（备查）**
- `users` 表当前**没有 email 字段**；但账号约定是「工号 = 邮箱前缀」，可用 `email = username@MAIL_DOMAIN`（`MAIL_DOMAIN` 走 .env）推导，存量账号零迁移；非企业邮箱账号才需单独存 email。
- 新增 `password_resets` 表：token 哈希 / 工号 / 到期 / 是否已用 / 请求 IP。
- 安全：token 只存哈希、一次性、30 分钟过期；页面不暴露账号是否存在；同工号 10 分钟最多 1 封、同 IP 每小时最多 5 次；请求与完成都写日志。
- 新增页面：登录页「忘记密码」弹窗 + `/reset?token=` 设置新密码页。

**待决策（下次讨论时先定这三条）**
1. 企业邮箱 SMTP / 内部中继能否申请到？（决定 C 能不能做）
2. 先做 B（不依赖 SMTP，当天可用）还是等 SMTP 直接做 C？
3. 账号表是否现在就加 `email` 字段（B 用不上，C 必须先有）。

## T6 摘要（2026-11-04 记录 · 主人决定「晚点再处理」，与其它采集改动合并做）

**问题**：Win11 24H2 起微软从系统里移除了 `wmic`，采集脚本里所有 `wmic ...` 调用直接报
`'wmic' 不是内部或外部命令`，后果：
- 软件清单（已安装程序）空采集
- 部分硬件信息（主板/内存条明细/磁盘序列号等依赖 wmic 的字段）缺失
- 采集包本身仍然成功生成，所以**问题不会报错，只会静悄悄少数据**（最麻烦的一类）

**替换方案**（届时照此改）

| 原 wmic 用法 | 替换为 |
|---|---|
| `wmic product get name,version` | `Get-CimInstance Win32_Product`（很慢，建议改读注册表 `HKLM\...\Uninstall\*` 的 DisplayName/DisplayVersion） |
| `wmic computersystem get ...` | `Get-CimInstance Win32_ComputerSystem` |
| `wmic bios get ...` | `Get-CimInstance Win32_BIOS` |
| `wmic diskdrive get ...` | `Get-CimInstance Win32_DiskDrive` |
| `wmic memorychip get ...` | `Get-CimInstance Win32_PhysicalMemory` |
| `wmic path win32_VideoController get ...` | `Get-CimInstance Win32_VideoController` |

**兼容性要求（重要）**
- 新老系统都要能跑：`Get-CimInstance` 从 Win8 起就有，Win7 需 PowerShell 3+；脚本里做「有 CIM 用 CIM，没有回退 wmic」的双路径，别一刀切。
- 这是**客户机侧**改动 → 影响已经分发的桥接器/采集脚本，必须和其它采集改动**一次性合并**，避免客户机反复重发（主人明确要求）。
- 采集脚本是服务端下发的（`static/tools/` 或 tslog 逻辑），改完老客户端不用重装即可生效——但要验证实际走的是下发路径，不是桥接器内置的老副本。

**验收标准**
- 在 Win11 24H2 机器上跑一次日志采集，包内软件清单条数 > 50、硬件字段无空值
- 在 Win10/旧 Win11 上回归一次，结果与改动前一致（不退化）
- 采集日志里不再出现 `'wmic' 不是内部或外部命令`

## T8 摘要（2026-11-05 记录 · 主人决定先硬拦）

**现状**：创建房间前用联想官网 ASP 校验 SN（`/api/sn_check` → 旁挂 `/asp_warranty`）。
官网**连不上**（超时/5xx）时接口返回 503，前端红灯 + 创建按钮禁用，后端 `/api/rooms` 也直接拒建。

**为什么这么定**：宁可挡住，也不要让假 SN（如 `12345`）建出房间。

**待优化点**：官网抖动会造成"全公司建不了房"。后续可选方案：
- 失败重试 N 次后再放宽（灰灯 + 允许创建 + 房间标「SN 未经官网校验」）
- 或做本地 SN 缓存（最近校验过的 SN 在 TTL 内离线放行）
- 或只对 `admin` 放行

## T9 摘要（2026-11-05 记录）

**问题**：左栏「工单」语义是**进行中工单**。魔方 `device_info` 只给「该设备当前进行中工单数为 N」，
不给单号；历史工单号（如 `202511252170047019`）属于「历史维修记录」，**绝不能**回填到工单栏。
当前实现：工单栏空 → 显示「无进行中工单」。

**要显示真实在修单号需要**：调用魔方「进行中维修记录」子流程（前端有「点击查看进行中维修记录」快捷按钮，
对应另一套工作流），预计 15~20 秒。建议仅在「进行中工单数 > 0」时按需触发，别拖慢常规打开房间。

## T11 摘要（2026-11-11 记录）

**背景**：ThinkLogParser 对单包 IDG 有事件缓存上限 —— **50 万条 / 1 GiB / 单条 1 MiB**。
联想官方 tslog 采集器导 444 个渠道，普通台式机实测 **507,750 条**、X1 Carbon **509,788 条**，
整包必被拒（`IDG 事件缓存超限…请按设备或时间拆包`）。

**当前临时做法（B 方案，服务端 1.8.3 起）**：
上传前先数事件 → 超过 47 万条则按「噪音渠道优先」裁剪（Hyper-V VmSwitch/Compute、Store、Ntfs、
SMB、StateRepository、PowerShell、Defender…）→ 重打包（保留 tslog/ 结构）→ 再上传。
永不裁剪：System / Application / Security / HardwareEvents / Setup / Kernel-PnP / Storport + 全部 txt/dump。
实测 509,788 → 455,487 条（只掉 1 个渠道），总耗时 117 秒；原包始终保留在客户机 `C:\DiagLogs`。

**到期要做的恢复动作**：
1. `.env` 设 `IDG_PRESCAN=0`（关掉上传前预扫裁剪）
2. 同时把「上传失败后自动裁剪重传」的兜底一并去掉（`_tlp_deliver` 里 `缓存超限` 分支）
3. 或在平台提额后把 `IDG_EVENT_TARGET` 调到新上限之上（比重更大时仍用预扫，仅作提示）
4. 恢复后用同一个超限包（`2e6b418c…` / `7c1debc5…` 类型）复测一次完整包上传，确认平台接收
5. 轨迹里 `thinklog.sent` 事件的 `trimmed` 字段应消失，作为「已恢复完整上传」的验证点

**风险提示**：裁剪期间平台侧记录的是裁剪包，若后续需要全量分析，必须人工上传客户机上的原始整包。

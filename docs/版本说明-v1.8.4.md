# Nexpert v1.8.4 版本说明（对比 v1.6.8）

> 上一个已发布版本：**v1.6.8（2026-11-05）**。此后 v1.6.9 ~ v1.8.3 的改动都集中在本地开发环境，
> 本次一并发布为 **v1.8.4**。
> 版本矩阵：**服务端 1.8.4** / 现场作业台 **v0.18.7** / 二线控制台 **v0.22.1** / 桥接器 1.4.4（源码未改动，无需重新分发）。

一句话：**诊断从「跑一组命令看输出」变成「按现象走完一条判定—修复—复测—结单的闭环」；日志投递从自建签名直链换成联想官方 TLP CLI；实用工具从多步执行计划改成一步直读。**

---

## 一、快捷诊断：5 段式诊断流程（本版最大改动）

### 背景

旧版快捷诊断是「点一张卡 → 看一份执行计划 → 跑一串只读命令 → 输出一堆原始文本」，
结论要工程师自己下。分析 33.6 万条历史工单后（换件率 72.7%），确定要按**故障现象**组织诊断，
而不是按技术名词。

### 新流程

```
S0 选现象（客户说得出口的话：死机蓝屏 / 自动重启 / 卡顿 / 花屏闪屏）
S1 取证（3~8 项，单项失败不中断，逐项反馈）
S2 AI 判定（硬件 / 软件 + 置信度 + 逐条引用本次采到的证据）
S3 软件修复（白名单动作，L1 免审批 / L2·L3 需人工确认）
S4 复测（按该修复声明的验证指标，不看 exit_code）
出口 A 复测通过 → 结单（写入人机分工说明，可下载诊断报告）
出口 B 复测不通过 或 判定硬件/证据不足 → 采集日志 + 投递平台 + 出报告转现场
```

### 实现

| 层 | 实现 |
|---|---|
| 后端流程定义 | `server.py` 新增 `DIAG_FLOW_LABELS`（现象 → 取证项）与 `DIAG_FIX_SPECS`（修复白名单） |
| 接口 | `GET /api/diag_flow/spec?action_key=bsod\|reboot\|slow\|display` → `{steps[], count_step, supported}` |
| 前端 | 现场台/二线台新增 `#dfMask/#dfDlg/#dfBody` 对话框 + `window.DiagFlow`（约 390 行），捕获阶段拦截这 4 张卡片的点击，阻止其退回「执行计划」 |
| 修复白名单 | `bsod_sfc`(L3 SFC+DISM)、`bsod_dump_on`(L2 开转储)、`reboot_faststartup`(L2 关快速启动)、`slow_cleanup`(L1 清临时文件)、`slow_sfc`(L3)、`display_tdr_extend`(L2 延长 TDR)、`display_rescan`(L2 重新扫描设备)，每项都带 `verify_kind/verify_cmd/verify_desc` |
| 判定纪律 | **AI 只能从白名单里挑 id，不能自由生成命令**；置信度 < 0.6 或关键证据缺失必须输出「不确定」且不给修复 |
| 问题卡改名 | `quick_diagnoses.json` 按客户口径重写现象标签（如「硬件报错（WHEA/内存）」→「花屏·黑屏·闪屏·亮线」），技术名词只出现在卡片内的【事实观察】 |

### 验收（假桥接器 + 真前端点击，二线台）

| 卡片 | 取证 | AI 判定 | 修复 | 复测 / 出口 |
|---|---|---|---|---|
| 死机、蓝屏 | 6/6（异常 4） | 软件 68%（0x1a + minidump + 41×3；WHEA/TDR 为空） | SFC(L3) / 开转储(L2)，均需确认 | — |
| 自动重启 | 5/5（异常 4） | 软件 68% | 2 张 L2 → 确认弹窗 → 执行 | 复测通过：41/6008 修复前 3 条 → 复测 0 条 |
| 卡顿 | 5/5（异常 5） | 软件 68%（C 盘剩 4.2GB、第三方自启） | 1 张 L1 免确认 | 复测通过：TEMP 3120MB→180MB → 结单 |
| 花屏、闪屏 | 5/5（异常 5） | **硬件 80%**（Display 4101 ×2 `nvlddmkm 停止响应`） | **0 张**（硬件不远程修） | 出口 B：采集日志出报告转现场 |

## 二、日志投递：改走 TLP CLI 0.4.0

### 背景

旧实现是自签 JWT + `/api/upload_link` / `/api/info` / `/api/query` 三段式，受网关 60 秒与
上行带宽限制，**6 MB 以上的包必然超时**（11 MB 包实测 504）。联想官方 CLI 提供 2 GiB 上限、
8 MiB 分块续传与幂等请求编号，直接替换。

### 新链路

```
一键采集 → 客户机打 tslog 7z
        → 上传前预扫事件条数（IDG 包）
        → 服务端调 tlp logs upload（分块续传、幂等 request_id）
        → 平台识别为 IDG 类型，返回 logid
        → 写回房间，页面显示解析链接
```

### 实现

| 项 | 实现 |
|---|---|
| 投递 | `server.py` 新增 `TLP_BIN/TLP_TIMEOUT/TLP_SEARCH_BASE` 与 `_tlp_upload()`：`asyncio.create_subprocess_exec` 调 `tlp logs upload <file> --request-id cds-<房间>-<时间戳>`，解析 stdout JSON |
| 异步化 | `POST /api/thinklog/send` 立即返回 202 + `request_id`，后台任务执行上传；新增 `GET /api/thinklog/state?room_code=` 供页面每 3 秒轮询（解决网关 60 秒超时） |
| 包名可读 | 平台按真实文件名入库 → 用**同盘硬链接**改名成 `机型_SN_jobid.7z`（零拷贝），上传后自动清理 |
| 删旧实现 | 移除自签 JWT、upload/info/query 三段式、公网签名下载路由 `/api/thinklog/fetch/*`，共删约 3,500 行死代码 |
| 环境 | `.env` 增加 `TLP_BIN / TLP_CONFIG / TLP_TIMEOUT / TLP_SEARCH_BASE`，`THINKLOG_VIEW` 指向 dev；删除 6 个废弃变量 |

### IDG 事件缓存上限（50 万条）处理

平台对单包 IDG 的事件索引上限是 **50 万条 / 1 GiB / 单条 1 MiB**。联想官方 tslog 采集器会导出
**444 个渠道**，实测一台普通台式机 **507,750 条**、X1 Carbon **509,788 条** —— 整包必被拒。

实现（`_idg_trim` + `_idg_count_events`）：

1. **上传前预扫**：解包 → 用 python-evtx 逐文件数事件（444 个文件约 4.5 秒）
2. 总数 ≤ 47 万 → 直接传原包；> 47 万 → 按**噪音渠道优先**裁剪（Hyper-V VmSwitch / Compute、Store、
   Ntfs、SMB、StateRepository、PowerShell、Defender…），保留 tslog/ 结构重打包后上传
3. **永不裁剪**：System / Application / Security / HardwareEvents / Setup / Kernel-PnP / Storport
   以及全部 txt、dump、配置快照
4. 兜底：预扫未拦住时，命中「缓存超限」错误仍会自动裁剪重传一次
5. 页面提示裁掉了哪些渠道；**原始整包始终保留在客户机 `C:\DiagLogs`**

实测：509,788 → 455,487 条（只掉 1 个渠道），总耗时从 200.6 秒降到 **117.1 秒**，且平台侧不再产生失败记录。

> ⚠️ 已在 `docs/待办清单.md` 记为 **T11**：平台侧放宽后必须恢复上传完整日志包（关 `IDG_PRESCAN` 并去掉兜底分支）。

### ThinkLogParser 字段对齐

按平台前端反查的真实字段规范投递：`case_number=Logs-YYYYMMDD-xxxx`、`source=ThinkLogParser`、
工单号进 `ir_id`，否则平台列表/按 SN 搜索都搜不到我方上传记录。

## 三、实用工具：从多步执行计划改为一步直读

旧版实用工具卡都是「4 步执行计划 → 采集 → 输出原始文本」，而且 `bio`、`hw_smart` 这类卡
在后端根本没有执行实现（`/api/action_steps/<key>` 返回 `supported:false`），点了没反应。

本版统一改为**点击即直读**（结果挂独立容器 `#directPanel`，避免被计划面板的定时重绘清空）：

| 卡片 | 后端 | 输出 |
|---|---|---|
| 开机自启动 | `ACTION_STEP_SPECS["startup"]` + `POST /api/startup/toggle` | 分类表格（第三方/计划任务/服务/系统项），带状态徽标与禁用/启用按钮 |
| 驱动版本对账 | `POST /api/drivers/reconcile` | 本机 vs 官网差异表（落后/一致/本机更新/定制件/无法比较）+ 下载按钮 |
| 硬盘健康 | `POST /api/tools/smart/assess` | 每块盘结论（正常/注意/危险）+ 判读依据 + 原始输出折叠 |
| BIOS 信息 | `POST /api/tools/bios/read` | BIOS 版本/日期/厂商/SN + 启动模式/安全启动/TPM/虚拟化/硬盘模式 + 全量设置项 |

同时删除：OA3 密钥激活、驱动安装/升级（写操作）、官方驱动清单、本机已装驱动（后两者合并为驱动版本对账）；
SN/MTM 写入移到分组最后；删除「实用工具」分组说明文案。

### 开机自启动的两个修复

1. **PowerShell `InvalidVariableReference`**：上一版把注册表路径写成 `"$:\Software\..."`（`${h}` 的插值在
   双层转义中丢失），整条脚本不解析 → 页面只剩「1 项 · 未分类」。现在改为显式两条路径 + 带状态解析，
   并用 `ConvertTo-Json` 强制数组输出（单条结果不再被拆成对象）。
2. **系统项误判为可禁用**：`%windir%\system32\...` 这类（SecurityHealth、OneDriveSetup）之前判成「第三方可禁用」，
   现在系统目录一律判系统项、不给禁用按钮。

### 硬盘健康的判定重构（两次纠错）

1. **`重映射扇区 80000` 假告警**：NVMe 盘的 smartctl 输出里有「Supported Power States」表，第 5 档那行
   （` 5 - 0.0500W ... 5000 80000`）被 ATA 属性解析误当成 ID#5 `Reallocated_Sector_Ct`，把最后的
   `Ex_Lat 80000` 当成了坏道数 —— 一块健康的 SSD 被判「危险」。现在 NVMe 完全跳过 ATA 解析，
   ATA 只在 `ID# ATTRIBUTE_NAME` 表头之后解析。
2. **判据不再自创阈值**：只认设备/厂商自己的判定 —— `overall-health` 非 PASSED、属性 `WHEN_FAILED` 非 `-`、
   属性 `VALUE ≤ THRESH`、NVMe `Critical Warning ≠ 0`、`Available Spare ≤ Threshold`、介质错误 > 0 → 危险；
   计数类 raw > 0 但厂商未判失败 → **注意**（并注明「厂商尚未判失败」）。同时按介质区分措辞（SSD 说坏块、HDD 说坏道）。

## 四、驱动版本对账（新功能）

把原「官方驱动清单」与「本机已装驱动」两张卡合并为一张，一次点击完成对账：

| 步骤 | 实现 |
|---|---|
| 读本机 | `Win32_PnPSignedDriver` → 设备名/厂商/版本/设备类/INF 名，去重 |
| 拉官网 | 联想官网 `drive_listnew` 按 **SN**（实测官网认 SN 不认 MTM，MTM 返回 `101404 no data2`） |
| 匹配 | **全局打分贪心**：型号关键词 +100、厂商一致 +40、设备类 +30；官网写了厂商而本机不符则拒绝匹配（避免「AMD 显卡驱动」配上 Intel 核显）；只按设备类匹配的低置信项标「需人工确认」 |
| 版本比较 | 四段数字逐段比较；官网版本字段是复合描述（`I210/I350:14.1.22.0;X550:...`）或版本体系差 10 倍以上 → 判「无法比较」 |
| 建议 | **只有「落后 + 厂商一致」才计入建议升级**；本机版本更高或厂商不一致（OEM 定制件）只展示不推荐 |

实测（SN GM09NMT9）：官网 88 条 → 过滤非驱动/同名去重后 34 条，落后 11 · 一致 8 · 本机更新 6 · 定制件 1 · 无法比较 8。

## 五、二线控制台收敛

- **快捷诊断只保留 4 张现象卡**（死机蓝屏 / 自动重启 / 卡顿 / 花屏闪屏），旧的「归档」组 38 张不再出现在快捷诊断；
  同时把现场端的 5 段式诊断流程（`DiagFlow`）注入二线台，两张控制台行为完全一致。
- 删除 OA3 密钥激活、驱动安装/升级卡片（连同演示串与端点映射、无效过滤名单）。
- SN/MTM 写入移到「实用工具」最后一位。
- 修：**切换分组时清理残留结果**（从实用工具切到快捷诊断，直读结果与执行计划面板不再留在下方）。

## 七、升级要点

1. **必须安装 TLP CLI 0.4.0 并完成授权**（`tlp login --channel claw --no-browser`，授权时勾选
   「允许上传日志」与「允许生成报告草稿」）；`.env` 配 `TLP_BIN`。授权最长三个日历月，过期需人重新授权。
2. `.env` 新增：`TLP_BIN`、`TLP_CONFIG`、`TLP_TIMEOUT`、`TLP_SEARCH_BASE`、`IDG_PRESCAN`、
   `IDG_EVENT_TARGET`、`IDG_PRESCAN_MAX_MB`；`THINKLOG_VIEW` 改为 dev 解析页地址。
3. 删除的 `.env` 变量：`THINKLOG_JWT_SECRET`、`THINKLOG_API`、`THINKLOG_UPLOAD_API`、`THINKLOG_INFO_API`、
   `THINKLOG_QUERY_API`、`THINKLOG_PARSE_WAIT`。
4. 服务端依赖 python-evtx（IDG 事件计数），装在 log-analyzer 的 venv 里，路径由 `IDG_PY` 指定。
5. 桥接器二进制**未改动**，无需重新分发；`tslog` 采集包结构未变。
